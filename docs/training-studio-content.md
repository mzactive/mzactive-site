# MZA Training Studio — MVP content policy
The 83-entry bilingual starter catalog is independently authored, consisting of common exercise names, original Arabic translations and short factual category/equipment tags. It contains no third-party images or videos and no default training prescription. Coaches choose the dose.
The existing saved-program workout library remains available as a separate feature. Custom exercises are stored in this browser, namespaced to the authenticated approved coach ID; they are not a cloud-synced or encrypted storage solution. Do not store confidential athlete information in custom exercise names.
External candidate: https://github.com/yuhonas/free-exercise-db declares the Unlicense in LICENSE.md; upstream image provenance requires independent verification. Another candidate is wger, whose initial exercise data is CC BY-SA 3.0 (https://wger.readthedocs.io/en/2.4/); individual media rights and attribution must be reviewed. No assets from that repository have been copied. Future media import requires documented creator, original source, license, attribution and commercial/derivative permissions per asset. No paid API.
The picker appends readable session text to the existing program editor and uses existing save/send endpoints. No backend migration or production deployment is needed to test this branch.

The expanded MVP includes copy/paste individual workouts and weeks, date-relative browser-local program templates, new-program reset, and an athlete weekly calendar with completion logs written through the existing authorized completion API. Templates exclude dedicated athlete identity fields, but free-text workout instructions may contain personal information; avoid adding it. Real browser mobile testing is simulated Chromium, not physical devices. No production deployment or full TrainHeroic feature parity is claimed.

Coach workspace: approved sports/bodybuilding coaches can open a dedicated full-width workspace at dashboard.html?studio=1, using the same authenticated data and existing editor. The legacy dashboard remains reachable and the workspace is opt-in pending production validation.

The calendar-first workspace is now the default for approved sports/bodybuilding coaches on the standard dashboard URL. Classic dashboard remains available using ?studio=0, and existing program/connection deep links remain on the original path. Exercise and program-template libraries have their own screens; the original editor and API remain the source of truth. Send-to-athlete resolves the selected connection to its accepted athlete user ID via the existing authorized connections API. No new backend or database changes.

## Standalone calendar workspace (coach-studio.html)
This is a separate, opt-in, from-scratch coach UI. Approved sports and bodybuilding coaches see only their accepted active coaching connections; calendar drafts are scoped by coach account, athlete connection and week in the current browser tab. Existing assigned programs and completion logs are read-only in this UI. A new structured workout is serialized into the current legacy workout format. Publishing uses the existing two-step API: create unassigned, then assign to the verified athlete user ID. The existing backend requires a real phone number; do not invent one. If an acknowledged create succeeds but send fails, the current-tab draft remembers the program ID for retry. Network failure before create acknowledgement can still leave an unassigned server program; the new UI is not an exactly-once server transaction. Reusable templates are browser-local; do not include private athlete information. No backend schema, assistant-coach permissions, per-set athlete logging, team assignment, or licensed media have been added yet. Existing coach and athlete pages remain available.

### Account library storage
The private account library API uses additive migration 0044 and revision-checked per-item writes for exercises, workouts and weekly program templates. Approved sports/bodybuilding coaches only; no shared staff or athlete data access. Once the API is available, the workspace uses the server library and offers explicit, non-overwriting import of browser-local items. Before backend deployment it clearly uses browser-only storage. A previously connected account library blocks editing during API failure rather than silently creating a second divergent library. Calendar drafts and existing published program workflows remain unchanged. Run backend and browser regression tests; apply migration to the dedicated preview D1 before a preview Worker deployment. Production preflight intentionally blocks release until the owner reviews and enables it. Do not bypass this guard. No production database or Worker change is included in a GitHub Pages deployment.
